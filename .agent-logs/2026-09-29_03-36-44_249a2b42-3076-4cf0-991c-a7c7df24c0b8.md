**The key decision: video generation runs as a background job.** A Veo video takes minutes to generate, which is longer than a serverless function is allowed to run. So every generation, including images for consistency, will work like this:
1. Save a `generations` row with status `queued`.
2. Start the job with the provider and save its operation ID.
3. Poll for the result, then save the output to Supabase Storage and set the status to `done` or `failed`.
4. The UI updates live through Supabase Realtime.

This is also what makes the experience feel good: you submit a prompt, a placeholder card appears straight away, and it fills in when the result is ready.

## Setting up Google sign-in

There's a common trap here: the Supabase guide's summary makes it look as if Google should redirect straight back to your app. It shouldn't. **Google redirects to Supabase, and Supabase then redirects to your app.** Two different URLs go in two different places.

### Part A: Get your Supabase callback URL
1. Open the Supabase dashboard → your project → **Authentication → Sign In / Providers → Google**.
2. Copy the **Callback URL** shown there. It looks like `https://<your-project-ref>.supabase.co/auth/v1/callback`.
3. Leave this tab open. You'll paste the Google keys here in Part C.

### Part B: Google Cloud Console
1. Go to [console.cloud.google.com](https://console.cloud.google.com) and create a project, for example **OneShot**.
2. Open **Google Auth Platform** ([console.cloud.google.com/auth/overview](https://console.cloud.google.com/auth/overview)) → **Get started**:
   - **App name:** OneShot. **Support email:** your Gmail.
   - **Audience:** External.
   - **Contact email:** your Gmail. Agree to the policy, then click **Create**.
3. **Data Access** → **Add or remove scopes**: tick `.../auth/userinfo.email`, `.../auth/userinfo.profile` and `openid`, then **Save**.
4. **Clients** → **Create client**:
   - **Application type:** Web application. **Name:** OneShot Web.
   - **Authorized JavaScript origins:** `http://localhost:3000`
   - **Authorized redirect URIs:** the **Supabase callback URL from Part A**, not a localhost URL.
   - Click **Create**, then copy the **Client ID** and **Client Secret**.
5. **Audience** → **Publish app** → confirm.
   - This matters for the assignment. In "Testing" mode, only the Google accounts you list can sign in, so reviewers would be locked out.
   - We only ask for email and profile, so Google doesn't need to review the app. It may show a notice about verification, but publishing still works.

### Part C: Back in Supabase
1. **Authentication → Sign In / Providers → Google**: switch it **on**, paste the **Client ID** and **Client Secret**, then **Save**.
   - The secret goes only into the Supabase dashboard. It doesn't need to be in `.env.local`.
2. **Authentication → URL Configuration**:
   - **Site URL:** `http://localhost:3000` for now. We'll change it to the Vercel URL when we deploy.
   - **Redirect URLs** → **Add URL:** `http://localhost:3000/auth/callback`
3. **Email magic link:** under **Sign In / Providers → Email**, make sure it's enabled. It is by default.
   - Supabase's built-in email sender only allows a few emails per hour. That's fine for building and testing. Before launch we can connect a proper email service such as Resend.

### When we deploy (later, in M1)
- In Google, add the Vercel URL, for example `https://oneshot.vercel.app`, to the **Authorized JavaScript origins**.
- In Supabase, change the **Site URL** to that address, and add `https://<vercel-url>/auth/callback` to the **Redirect URLs**.
